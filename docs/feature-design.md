## 1. システム概要・業務フロー

### 大目的

プロジェクトで扱う製品と実施すべきフェーズを選択（要/不要）し、選択された製品・フェーズに対して実施計画を立て、その計画に沿ってタスク管理・進捗管理を行う。

### 業務フロー

```
① プロジェクト設計  →  ② 実施計画立案  →  ③ タスク管理  →  ④ 進捗監視
（製品×フェーズ選択）    （日程・担当者）    （日常作業）     （アラート・報告）
```

#### 製品×フェーズ要否判定のUI

```
製品X  [✅] 初回リリース  [✅] 仕様変更  [✗] バージョンアップ  [✅] 保守
```

### ブロック2: 実施計画立案 ―「いつ・誰が・どの順でやるか」を決める

#### 実施計画立案でやること

| ステップ | 内容 |
|----------|------|
| 日程設定 | フェーズごとに開始日・完了期日を決める |
| タスク登録 | フェーズ配下のタスクを登録 |
| 担当者アサイン | タスク群への担当者割り当て |
| フェーズ間の順序設定 | 「フェーズA完了後にフェーズBを開始」等の依存設定 |
| 計画承認 | PM による計画全体の承認 |

#### 計画立案の方式（検討結果）

##### 採用方式: 逆算スケジューリング ＋ 過去プロジェクトのコピー

**背景と課題:**
- 完了予定日が先に決まっており、そこから逆算して各タスクの日付を決める必要がある
- テンプレート方式は「標準工数」で対応できないため不適
- Excel インポートはユーザーごとに管理テンプレートが異なるため転記ミスが発生する

**逆算スケジューリング（案A）:**

```
完了期日: 2026/12/31 を入力

タスク名        所要日数  依存関係
────────────────────────────────
テスト          10日     ← 開発完了後
開発            30日     ← 設計完了後
設計            15日     ← 要件定義完了後
要件定義        10日     ← なし

            ↓ システムが自動計算

要件定義  2026/09/17 〜 2026/09/30
設計      2026/10/01 〜 2026/10/22
開発      2026/10/23 〜 2026/11/28
テスト    2026/11/29 〜 2026/12/31
```

- 「所要日数と順序」はプロジェクト間でほぼ共通 → 1回入力すれば資産になる
- 期日が変わっても所要日数は変わらないため再利用が容易

**過去プロジェクトのコピー（案B）:**

```
「プロジェクトAをコピー」
  → 新しい完了期日: 2027/03/31 を入力
  → 依存関係・順序・担当者ロールはそのまま
  → 全タスクの日付を自動再計算
  → 担当者を実名に置き換えるだけ
```

**推奨フロー:**

```
初回プロジェクト: 逆算スケジューリングで「所要日数＋順序」を入力 → 完了期日から自動計算
2回目以降:       過去プロジェクトをコピー → 完了期日だけ変更 → 完了
```

#### ガントチャートの活用

**方針: 「入力はシンプル一覧、確認はガントチャート」の分離**

```
【計画入力】スプレッドシート型一覧（編集）
  タスク名 | 担当者 | 所要日数 | 依存先
  ─────────────────────────────────
  要件定義  | 田中   | 10日     | -
  設計      | 佐藤   | 15日     | 要件定義
           ↓ 完了期日を入力 → 日付を自動計算

【計画確認】ガントチャート（閲覧専用）
  入力内容をガントチャートで視覚的に確認
  → 問題なければ「計画確定」ボタンで承認
```

**編集可能ガントチャートを採用しない理由:**

| 要因 | 内容 |
|------|------|
| 開発コスト | ドラッグ操作・依存矢印・リアルタイム再計算が必要で最も難易度が高い |
| 保守コスト | ライブラリバージョン追従・バグ修正が継続発生 |
| チーム状況 | 8名並行開発・AI駆動・初心者複数名という条件下では事故リスクが高い |
| 10年運用 | 複雑なガントチャートは技術的負債になりやすい |

ガントチャートは**閲覧専用のまま流用**し、既存 SCR002 をほぼそのまま使う。

## 3. データモデルの設計変更

### チケット階層の削減

**変更前（フェーズをチケット扱い・4段階）:**

```
Project
  └─ Product
       └─ Phase（チケット depth=0）
            └─ Task（チケット depth=1）
                 └─ SubTask（チケット depth=2）
                      └─ SubSubTask（チケット depth=3）
```

**変更後（フェーズを別テーブルで管理・2段階）:**

```
Project
  └─ Product
       └─ Phase（ProjectPhase テーブル）← フェーズは別管理
            └─ Task（チケット depth=0）
                 └─ SubTask（チケット depth=1）← 2段階のみ
```

**削減の効果:**

| 観点 | 4段階（変更前） | 2段階（変更後） |
|------|--------------|--------------|
| クエリ複雑度 | 再帰4段 | 再帰2段 |
| ガントチャート表示 | インデント4段 | インデント2段 |
| 進捗集計 | 曾孫まで集約 | 子まで集約 |
| N+1リスク | 高い | 低い |
| フェーズ完了判定 | 複雑 | シンプル |

**フェーズを別テーブルにする追加メリット:**
- 要否判断・計画立案・進捗俯瞰がフェーズ単位で自然に扱える
- フェーズ配下のチケットが全完了 → フェーズを自動クローズできる

### 追加が必要なデータモデル

| 追加モデル | 目的 | 関連既存モデル |
|------------|------|---------------|
| `ProjectPhase` | プロジェクト×製品×フェーズの要否 + 期日・状態 | `ProjectOrm`, `ProductOrm`, `ProductReleaseOrm` |
| `AuditLog` | 全監査証跡 | 全モデル |

## 4. タスクグループ自動完了の設計

### 動作仕様

グループ内のいずれかのチケットを完了にした際、グループ内の残りのチケットを一括完了できる機能。

### 確認ダイアログ（必須）

自動完了を即時実行せず、**必ず確認を挟む**。

```
チケットAを「完了」に変更
         ↓
┌─────────────────────────────────────────┐
│ このチケットはグループ「製品Xリリース」  │
│ に属しています。                         │
│                                          │
│ 以下のチケットも同時に完了にしますか？   │
│   ・チケットB「設計レビュー」            │
│   ・チケットC「テスト計画書作成」        │
│   ・チケットD「承認申請」                │
│   他 12件                                │
│                                          │
│  [はい、すべて完了にする]  [このチケットのみ完了] │
└─────────────────────────────────────────┘
```

件数が閾値（例: 5件）を超える場合は**入力確認も追加**。

```
┌──────────────────────────────────────────┐
│ 15件のチケットを同時に完了にします。      │
│                                           │
│ 確認のため「完了」と入力してください:     │
│ [ 完了        ]                           │
│                                           │
│  [確定]  [キャンセル]                     │
└──────────────────────────────────────────┘
```

### 誤操作後の救済

誤って一括完了した場合は、**チケット一括ステータス変更機能**で元に戻す。  
チケット自体は論理削除設計のため消えておらず、ステータスを戻すだけでよい。タスクの再作成は不要。

```
誤操作後の状態
  チケットB「設計レビュー」      status: closed  ← 誤って完了
  チケットC「テスト計画書作成」  status: closed  ← 誤って完了

救済操作
  → 一括ステータス変更でチェックして in_progress に戻す
```

**チケット一括ステータス変更は「便利機能」ではなく「誤操作からの回復手段」としても必須。**

### グループからの除外時の動作

チケットをグループから外す際、自動完了されたものについては確認ダイアログを表示。

```
チケットB「設計レビュー」をグループから外します。

このチケットは自動完了されています。
ステータスを「進行中」に戻しますか？

  [ステータスも戻す]  [ステータスはそのまま]  [キャンセル]
```

- 自動完了されたチケットの場合のみ表示（`auto_completed` フラグで管理）
- 元々完了していたものには表示しない
- 複数グループ所属・グループ再編目的での除外でも意図しない副作用が発生しない

## 5. 開発・保守コストの高い機能まとめ

### 採用しない・スコープを絞る機能

| 機能 | 理由 | 判断 |
|------|------|------|
| **編集可能ガントチャート** | ドラッグ操作・依存矢印・リアルタイム再計算が複雑。ライブラリ依存・保守負債 | **不採用 → 閲覧専用で代替** |
| **WebSocket リアルタイム通知** | 接続管理・認可・スケールアウト同期が複雑 | **不採用 → メール通知で代替** |
| **権限委譲** | ABAC条件が組み合わさり検証コストが跳ね上がる | **運用でカバーできるか確認要** |
| **期日変更承認フロー** | 通常の承認と別フローになり状態機械が二重管理になるリスク | **要否確認** |

### 実装済みで複雑さを増している機能

| 機能 | リスク | 対応方針 |
|------|--------|---------|
| **チケット4段階階層** | N+1クエリ・ガントチャート・進捗集計が全て複雑化 | **2段階に削減** |
| **タスクグループ自動完了** | エッジケース（誤操作・部分完了・却下混在）が多い | **確認ダイアログ＋入力確認で安全化** |
| **ファイルアップロード（ウイルススキャン）** | スキャンエンジン依存・バージョン管理・偽陰性対応が継続発生 | 継続監視 |

## 6. 実装優先度

```
優先度高（業務上の価値が高く、コストも低い）
  1. 製品×フェーズ 要否判定一覧（ブロック1-3）
  2. チケット更新・削除（ブロック3-1）
  3. チケット一括ステータス変更（ブロック3-7）

優先度中（価値が高いがコストも中程度）
  4. 実施計画立案（逆算スケジューリング）（ブロック2）
  5. 製品×フェーズ 進捗ダッシュボード（ブロック4-1）
  6. 期日アラートバッチ（ブロック5-2）

優先度低（価値はあるが再確認が必要）
  7. フェーズ完了自動判定（ブロック4-5）
  8. 過去プロジェクトのコピー機能（ブロック2）
  9. 進捗レポート出力（ブロック4-6）
```
